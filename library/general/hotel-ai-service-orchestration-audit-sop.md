# SOP: 酒店 AI 多意图服务编排、工单闭环与全链路审计标准实现

> **编号**: SOP-GENERAL-001  
> **分类**: 综合与系统架构 (`general`)  
> **标签**: 酒店AI, 多意图编排, 工单状态机, 全链路审计  
> **核心栈**: Node.js 20+, 原生 HTTP/HTML/JavaScript, PostgreSQL JSONB, WebSocket, SenseAudio ASR/S2, 高德 Web 服务, 知识库 API, node:test  
> **解决痛点**: 酒店住客的一段语音可能同时包含服务、设备、旅行和 FAQ 请求；若直接依赖单次模型输出，容易出现整句误转人工、工单越权流转、并发抢单、实时消息泄露、上游失败不可追踪及测试环境互相污染。  
> **复用定位**: 适用于“语音/文字输入 → 多意图拆分 → AI 与本地规则协同路由 → 工单/设备/旅行/知识库执行 → 角色定向实时推送 → PostgreSQL 可审计留痕”的酒店、园区、物业与客服中台。

## 1. 从 0 到 1 标准执行路径 (0-to-1 SOP)

### 阶段 1：先固化统一意图契约与安全降级

1. 将输入统一转换为结构化命令数组，每项至少包含 `action`、目标、操作、参数、置信度和原始子句；先用确定性规则拆分复合语句，再让模型补全语义。
2. 对设备参数做服务端归一化与边界收敛，例如空调温度限制为 16~30，灯光亮度和窗帘开合度限制为 0~100；模型输出即使是 Markdown 代码块或夹杂说明文字，也必须经过安全 JSON 提取。
3. 只把无法执行的子句转人工，不能因为一个子句未知就让整段请求失败；FAQ 作为旁路查询，不得破坏服务、设备和旅行主链路。
4. ASR/LLM/地图/知识库请求必须设置强超时、有限重试和降级策略。上游失败时保留仍可执行的本地命令与原始上下文。

**验收证据**：复合指令可以拆成多个动作；越界设备参数被收敛；模型不可用时仅未知子句转人工；上游密钥和完整响应不会出现在前端或公开日志。

### 阶段 2：以服务端状态机和事务建立工单闭环

1. 服务端是工单状态、房态和设备状态的唯一事实来源；客户端只能提交意图，不能直接改最终状态。
2. 工单状态严格限定为 `pending → dispatched → accepted → in_progress → completed`，并允许业务定义的 `rejected/cancelled/timeout` 终态；终态不可再次流转。
3. 抢单、接单和状态变更使用带旧状态、部门及经办人条件的原子 `UPDATE`，依据受影响行数判定并发冲突；所有变更同时写不可变审计日志和 `status_history`。
4. 为维修规则固化类别、P0/P1/P2 优先级、响应 SLA 和预计时长；后台扫描超时工单并产生领域事件，经理可以在审计留痕下派单或强制变更。

**验收证据**：并发接单只有一个成功；跨部门员工和非接单人不能推进工单；非法状态跃迁被拒绝；超时、取消、强制操作均可追溯。

### 阶段 3：将实时通知与请求审计做成独立侧车

1. 工单领域层只发出 `order.created/order.updated/order.timeout` 等事件；WebSocket 广播失败必须被吞掉并记录，不能回滚已经成功的工单事务。
2. WebSocket 握手复用 Cookie 会话鉴权，广播时按角色、部门、住客 ID 和房号过滤：经理可看全局，员工只看本部门，住客只看本人/本房间。
3. 每次请求建立统一 pipeline，记录 ASR、意图分析、服务派单、设备控制、旅行查询和知识库查询的输入摘要、状态、耗时、脱敏后的上游请求/响应及错误。
4. pipeline 正文、搜索索引、工单和 Token/积分用量统一落 PostgreSQL；记录生成内容哈希用于完整性校验，住客画像只从授权范围内的业务事实聚合。

**验收证据**：未登录 WebSocket 被拒绝；其他部门和其他住客收不到事件；断线采用指数退避重连；任一前端结果都能回溯到请求 ID、执行步骤和完整性校验。

### 阶段 4：以真实依赖边界完成联调、测试和交付

1. 单元测试覆盖纯函数、解析、边界收敛与降级；数据库/HTTP/WebSocket 集成测试使用独立测试库、唯一数据命名空间和明确的连接池所有权。
2. 严禁一个测试文件关闭仍被其他文件复用的全局连接池；清表、建表和服务监听必须在对应 suite 内成对创建与释放，避免“单测通过、全集失败”。
3. 为外部 SIP/AI 中台提供独立 Mock 模拟器，固定端口、请求字段、回调格式和端到端脚本；先验证本地纵切片，再接真实上游。
4. 部署前执行环境变量校验、数据库幂等建表/迁移、全量测试、端口检查和健康检查；API Key、数据库凭据只放服务端环境变量并在日志中脱敏。

**验收证据**：全量测试与各文件单独运行结果一致；Mock SIP 能完成单事件闭环；部署版本能通过健康检查、登录、语音/文本调度、工单流转、实时推送和审计查询。

## 2. 踩坑与返工自查清单 (Pitfalls & Checklist)

| 陷阱/现象 | 根本原因 | 标准解决姿势 |
| --- | --- | --- |
| 一条复合语音中只识别出一个动作，或整句转人工 | 把模型的一次分类当最终事实，没有本地拆句和逐子句降级 | 先拆复合子句并执行确定性规则，再用模型补全；只降级未知子句 |
| 模型返回代码围栏或解释文字导致 JSON 解析失败 | 直接 `JSON.parse` 原始响应 | 提取最外层 JSON、校验 schema、归一别名与数值范围，失败时返回安全 unknown |
| FAQ 查询改变主链路结果 | 将知识库问答混入统一意图分类并覆盖已有动作 | FAQ 采用 sidecar/旁路查询，从已知标题白名单推断，不覆盖可执行命令 |
| 两名员工同时抢到同一工单 | 先读后写，或更新条件没有包含旧状态与权限 | 使用条件 `UPDATE`/事务，以 `rowCount` 判定唯一成功者 |
| 同部门同事可以处理别人已接的工单 | 只校验部门，没有校验 `assignee_user_id` | 接单后普通员工只能操作自己的工单；经理例外并必须留审计日志 |
| WebSocket 把工单广播给无关用户 | 只按事件类型群发，没有绑定会话身份 | 握手鉴权，并按经理/部门/住客本人/房号进行服务端过滤 |
| 推送失败导致主业务失败 | 领域写入和网络广播耦合在同一事务 | 事务完成后发领域事件；广播异常隔离，客户端用重新拉取兜底 |
| 管理页面能看到结果，却无法解释上游过程 | 只存最终响应，没有统一请求管道 | 每一步保存状态、耗时、脱敏 I/O、错误和请求 ID，并建立可搜索索引 |
| 测试单文件通过、全集大量失败 | 多个 suite 共用全局 PostgreSQL pool、测试表和监听端口，某个 suite 提前 `end()` 或清表 | 独立测试数据库/schema；连接池由进程级 fixture 统一关闭；资源生命周期归属唯一 |
| 在受限执行环境中误判数据库功能失败 | 沙箱禁止本机端口或 PostgreSQL 不可达 | 区分环境性 `EPERM/ECONNREFUSED` 与断言失败；在获准的真实本机环境复测并记录前置条件 |

### 提交前 Checklist

- [ ] 复合指令、未知子句、FAQ 旁路和模型失败降级均有测试。
- [ ] 所有设备参数在服务端二次校验并限制范围。
- [ ] 工单流转、权限、并发抢单、终态不可变和超时扫描均有数据库集成测试。
- [ ] WebSocket 握手和每种角色的可见范围均有反向测试。
- [ ] Pipeline 上游 I/O 已脱敏，内容哈希可验证，API Key 不进入前端和仓库。
- [ ] 全量测试不依赖执行顺序，测试库、连接池和端口能确定性清理。
- [ ] Mock 联调和真实上游联调的配置、证据与失败边界被明确区分。

## 3. 面向 AI 的系统铁律 (Never do / Always do)

### 3.1 绝对禁止 (Never do)

1. **Never**：严禁把 LLM 输出当作已校验命令直接执行，尤其是设备数值、工单目标和权限字段。
2. **Never**：严禁因一个未知子句失败而丢弃同一请求中已经识别出的可执行动作。
3. **Never**：严禁让客户端直接修改工单终态、房态、设备状态或审计记录。
4. **Never**：严禁用“先查询、后无条件更新”实现抢单；也不得仅凭同部门身份操作已被他人接取的工单。
5. **Never**：严禁把 WebSocket 广播成功作为工单事务成功的必要条件，或向未通过服务端授权过滤的连接群发业务数据。
6. **Never**：严禁把 API Key、Cookie、音频正文、住客隐私或未经脱敏的上游响应写入公开日志、前端代码或提交记录。
7. **Never**：严禁让测试文件任意关闭共享连接池，或依靠固定端口、共享表数据和测试执行顺序获得通过。

### 3.2 必须遵循 (Always do)

1. **Always**：输入处理必须遵循“本地拆句/确定性规则 → 模型补全 → schema 校验 → 参数归一 → 逐子句执行/降级”。
2. **Always**：工单状态变更必须同时校验旧状态、角色、部门和接单人，并使用原子数据库操作处理并发。
3. **Always**：所有状态变化必须写不可变审计日志，并能通过请求 ID 关联原始输入、pipeline 步骤与最终结果。
4. **Always**：实时通道必须复用登录身份并按最小可见范围广播；客户端断线重连后要重新拉取权威状态。
5. **Always**：外部 AI、地图、知识库调用必须有超时、有限重试、脱敏记录和可用的业务降级。
6. **Always**：数据库 schema 初始化和迁移必须幂等；测试必须隔离数据、连接池和监听端口，并分别验证单测与全集。
7. **Always**：交付前必须用 Mock 和真实依赖边界各完成一次纵向闭环，并保存健康检查、接口响应、状态流转与审计证据。

## 4. 参考架构与关键模式

```text
[住客语音/文字]
       │
       ▼
[ASR + 本地拆句 + LLM 意图补全]
       │ schema 校验 / 参数收敛 / 逐子句降级
       ├──────────┬───────────┬───────────┐
       ▼          ▼           ▼           ▼
 [服务工单]   [设备控制]   [旅行查询]   [FAQ 旁路]
       │          │           │           │
       └──────────┴───────────┴───────────┘
                         │
                         ▼
          [PostgreSQL Pipeline + 索引 + 内容哈希]
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
       [角色过滤 WebSocket]   [管理后台/画像/审计]
```

### 原子抢单模式

```sql
UPDATE service_orders
SET status = 'accepted',
    assignee_user_id = $staff_id,
    accepted_at = now(),
    updated_at = now()
WHERE ticket_id = $ticket_id
  AND status = 'dispatched'
  AND target = $staff_department
RETURNING *;
```

以 `RETURNING` 是否返回记录作为唯一成功信号；成功后在同一事务写状态日志。不要先 `SELECT` 判断再无条件 `UPDATE`。

### 测试资源所有权模式

```text
process-level fixture:
  create isolated test database/schema
  create one pool
  run all suites with unique fixture ids
  close HTTP/WebSocket servers
  close pool exactly once
  drop isolated database/schema
```
