# SOP: 微信小程序 CloudBase + 云托管活动积分闭环

> **编号**: SOP-MINI-001
> **分类**: 小程序与移动端 (`miniprogram`)
> **标签**: 微信小程序, 云托管, CloudBase, 数据库事务, 积分运营
> **核心栈**: 微信小程序, wx.cloud.callContainer, CloudBase 文档型数据库, CloudBase 云存储, Node.js, Docker, 微信云托管
> **解决痛点**: 线下活动积分/兑换/核销全链路业务割裂、跨端鉴权与幂等扣减易超卖、云托管真实流量与开发环境调试不一致等工程痛点。
> **复用定位**: 适用于“活动内容运营 -> 用户登记/签到 -> 互动任务 -> 积分流水 -> 实体奖品兑换/现场核销 -> CRM 导出”的微信小程序项目。

---

## 1. 项目定位与核心上下文 (Context & Architecture)

### 1.1 业务目标

把一次线下活动变成可运营、可复用、可验收的用户闭环：运营人员发布活动和任务，用户在小程序登记并完成互动获得积分，积分可兑换实体奖励，现场人员凭凭证核销；登记信息、积分流水和订单可供运营后台导出。

### 1.2 边界与责任

| 层 | 责任 | 关键约束 |
| --- | --- | --- |
| 小程序用户端 | 展示活动、任务、积分、商品、凭证 | 通过 `wx.cloud.callContainer` 调用业务接口，不访问开发机 `127.0.0.1` |
| 云托管 API | 鉴权、活动/商品生命周期、任务完成、积分账本、兑换与核销 | 服务端是积分、库存、订单的唯一写入方 |
| 运营后台 | 录入/复制/发布/下架活动，管理任务和商品，查看订单并导出 | 已发布内容只下架，不硬删除历史引用 |
| CloudBase 文档数据库 | 持久化运营内容和业务状态 | MVP 可用单文档事务过渡；生产拆分用户、账本、库存、订单等集合 |
| CloudBase 云存储 | 活动 KV、流程图、商品图 | 保存 `fileID`；展示时换取临时 HTTPS 地址；往期照片保存外部云相册链接 |

### 1.3 MVP 与生产边界

- MVP 可使用一次性演示 `memberId`、种子目录和单文档事务，以便在没有真实活动和奖品时演示完整链路。
- 生产必须用微信 OpenID/UnionID（需要时叠加手机号授权），把用户、活动报名、积分流水、库存和订单拆成独立集合，并为管理员配置角色与审计日志。
- `TokenPlan` 在没有真实 Token 服务时只能标为“线上权益展示”，不得宣称已经发放 Token 或兑换码。

## 2. 从 0 到 1 标准执行路径 (0-to-1 SOP)

> 先用一条可证明闭环的纵切片打通业务，再扩展活动模板和运营能力。每阶段都必须留下可复核的输入、输出和证据。

### 阶段 1：固化规则与验收矩阵

1. 选定一个活动和 4~5 个可执行任务，例如：登记/签到、关注公众号或阅读资料、分享活动、NFC/产品介绍打卡、工程师演示核销。
2. 为每个任务写清 `taskId`、完成条件、积分、幂等键、是否需要人工核验和失败提示；同时定义活动的草稿/已发布/往期/下架状态。
3. 建立“登记 → 任务完成 → 积分明细 → 兑换 → 领取凭证 → 后台核销/导出”的验收表，区分演示数据与真实业务数据。

**输出/证据**：规则表、积分总分（演示可设为 100）、任务状态截图和一条端到端验收脚本。

### 阶段 2：建立数据模型与接口契约

1. 先定义活动、任务、奖品、用户资料、积分流水、兑换订单和凭证的字段及状态迁移；正文、议程、流程图、媒体和外部相册链接使用结构化字段。
2. 以仓储接口隔离文件模式与 CloudBase 模式。MVP 可把已有内容状态放在一个文档并用服务端事务 `mutate`，但不要让业务层绕过仓储直接读写数据库。
3. 固定公开接口（活动列表/详情、商品列表、用户状态、任务完成、兑换、凭证）和管理员接口（活动/商品 CRUD、发布/下架、媒体上传、订单核销、CSV 导出），统一返回 `{ ok, data }` 或 `{ error: { code, message } }`。
4. 为任务完成、兑换和核销定义幂等键与重复请求结果；积分变动必须产生不可变流水，余额只是可重算的快照。

**输出/证据**：字段/状态表、接口清单、错误码表、仓储契约测试和可导入的种子数据。

### 阶段 3：连接小程序、后台与媒体资源

1. 小程序初始化正确的 CloudBase 环境，统一用 `wx.cloud.callContainer`、`X-WX-SERVICE` 和 `/api/mvp`（或版本化 API 前缀）调用云托管；网络错误要提示“检查云托管服务/环境”，不能提示启动本机服务。
2. 后台表单支持活动 KV、文章块、议程、流程图、互动任务、外部云相册链接和奖品图；图片先校验 PNG/JPG/WebP 且小于 2 MB，再上传 CloudBase Storage。
3. 公开接口返回可用的临时 HTTPS 地址，模型同时保留 `fileID`；外部云相册只保存链接并提供复制/打开操作，不把整套历史照片复制进小程序包。
4. 维护演示目录迁移版本号：首次读取内容文档时幂等补齐演示活动和奖品，不覆盖运营人员已有记录，也不能因刷新反复新增。

**输出/证据**：后台发布一条活动和一件商品后，用户端能看到同一内容；图片加载、相册链接和任务配置在真机可复核。

### 阶段 4：验证、部署与运营交接

1. 本地先跑单元/契约测试、类型检查、`node --check`、`git diff --check` 和 Docker 构建；容器监听平台注入的 `PORT`，提供 `/health`。
2. 云托管创建新部署版本后，查看部署日志和实例状态，确认版本包含目标提交，并把已验证版本切到 100% 流量；旧版本先保留用于回滚。
3. 逐个冒烟 `/health`、公开活动/商品接口、用户状态/任务/兑换/凭证接口和 `/admin`；根路径返回 `Route not found` 不代表服务故障。
4. 清除微信开发者工具缓存并重新编译，真机完成“登记 → 4~5 个任务 → 积分明细 → 实体兑换 → 凭证 → 后台核销 → CRM CSV 导出”；保存版本号、请求结果和截图作为交接证据。

**输出/证据**：部署版本与流量记录、接口冒烟结果、真机闭环截图、回滚指针和运营操作手册。

## 3. 踩坑与返工自查清单 (Pitfalls & Checklist)

| 陷阱/现象 | 根本原因 | 标准解决/避坑姿势 |
| --- | --- | --- |
| 真机提示未连接服务，或仍要求启动本机后端 | 小程序仍请求 `127.0.0.1`/旧适配器 | 统一封装 `wx.cloud.callContainer`，配置 CloudBase 环境 ID 和服务名；清缓存后真机复测 |
| `/health` 为 200，但业务接口 404 | 云托管流量仍指向旧部署版本 | 对比部署提交/镜像摘要，验证 `/api/mvp/activity`、`/admin`，确认新版本 100% 流量后再编译小程序 |
| 后台新增一件商品后演示商品消失 | 前端静态目录与后台持久目录不是同一数据源，或写入时覆盖数组 | 服务器端按 ID 合并并保留种子目录；发布/上架是状态变更，不用整表覆盖 |
| 图片首次空白、刷新才出现 | 使用临时 URL、外部图片站不稳定或域名未加入合法域名 | 保存 CloudBase `fileID`，接口按需换取临时 URL；正式资源走已配置域名；小程序显示失败要有占位和重试 |
| 积分扣错、库存变负或重复兑换 | 客户端直接改余额，或扣分/扣库存/建单不是同一临界区 | 由服务端事务/乐观锁重试完成，使用幂等键；每次变动写积分流水，失败整体回滚 |
| TokenPlan 被当成真实线上兑换 | 展示商品没有真实 Token 发放系统 | 商品明确标注“线上权益展示/演示”，真实发放前禁止显示兑换成功或生成兑换码 |
| 已发布活动被硬删除后历史订单无法追溯 | 内容删除没有考虑历史引用 | 已发布/往期只做下架或归档；仅允许无引用草稿硬删除 |
| 密钥泄露或云端权限过大 | SecretId/SecretKey、管理员 Token 写入代码/日志或使用主账号 | 仅放云托管环境变量；使用最小权限子账号；日志脱敏，轮换凭据后重新部署 |
| 图片/代码进入错误分包，编译或预览失败 | `app.json` 页面与 `subPackages` 重复/路径漂移，或主包膨胀 | 页面只归属一个包；构建前检查路由与包体；媒体放云存储，避免把大图塞入主包 |
| 部署后仍看到旧内容 | 浏览器、微信开发者工具或接口缓存 | 记录版本号，清除编译缓存并重启页面；接口增加可观察版本字段，不能用刷新掩盖部署问题 |

### 启动前 / 提交前 / 演示前 Checklist

- [ ] 规则矩阵、积分总分、任务幂等键和失败提示已确认。
- [ ] `REPOSITORY_KIND`、CloudBase 环境 ID、服务名和 `ADMIN_TOKEN` 只在环境变量中配置，缺失时明确失败。
- [ ] 活动/奖品/积分/订单的状态迁移和审计字段已定义；没有客户端余额写接口。
- [ ] 媒体小于 2 MB、使用合法 HTTPS/fileID；外部云相册链接可打开。
- [ ] `/health` 与业务接口均命中新版本；云托管流量为 100%，旧版本仍可回滚。
- [ ] `npm test`、类型检查、Docker 构建和真机端到端链路通过。
- [ ] CRM CSV 不含不必要的隐私字段，导出权限与保存期限已约定。

## 4. 最佳实现与代码模式 (Best Practices & Patterns)

### 4.1 统一的小程序云托管请求包装

```javascript
function callMvp(path, method, data) {
  return new Promise((resolve, reject) => {
    wx.cloud.callContainer({
      config: { env: CLOUD_ENV_ID },
      path: '/api/mvp' + path,
      method: method || 'GET',
      data: data || {},
      header: { 'content-type': 'application/json', 'X-WX-SERVICE': CLOUD_SERVICE },
      success(res) {
        const body = res.data || {};
        if (res.statusCode >= 200 && res.statusCode < 300 && body.ok) return resolve(body.data);
        reject(new Error(body.message || '云托管业务请求失败'));
      },
      fail: reject
    });
  });
}
```

请求包装只负责传输和错误归一化；积分规则、权限和状态迁移必须留在服务端。

### 4.2 服务端原子兑换与幂等

```text
idempotencyKey = memberId + activityId + rewardId + clientRequestId
transaction:
  read member, reward, existing order
  if existing order: return the original order (idempotent)
  assert member.points >= reward.cost and reward.stock > 0
  decrement points and stock
  append immutable point_ledger(delta = -cost)
  create pending-pickup order and voucher
commit or retry on version conflict
```

核销接口同样按订单 ID 幂等：第一次将 `pending-pickup` 改为 `picked-up`，后续重复请求返回同一凭证和核销时间。

### 4.3 媒体与外部相册契约

```json
{
  "cover": { "fileId": "cloud://...", "url": "https://...", "expiresAt": "..." },
  "processImage": { "fileId": "cloud://...", "url": "https://...", "expiresAt": "..." },
  "albums": [{ "title": "活动云相册", "externalUrl": "https://..." }]
}
```

持久字段以 `fileId`/`externalUrl` 为准；`url` 是可刷新展示值，不能作为永久资产唯一标识。

## 5. 面向后续 AI 的系统铁律 (Agent Instructions)

### Never do

1. **Never** 把 SecretId、SecretKey、管理员 Token、真实用户资料或运行时数据库提交到代码仓库、截图和日志。
2. **Never** 让小程序客户端直接写积分余额、库存、订单或凭证；客户端只能提交意图，服务端校验并落账。
3. **Never** 把本机 `127.0.0.1`、一次性演示 `memberId` 或展示型 TokenPlan 当成生产依赖。
4. **Never** 用临时图片 URL 当永久资源，也不要把往期云相册的全部照片复制进小程序包。
5. **Never** 硬删除已发布活动、奖品和已有订单；必须保留历史引用并执行下架/归档。
6. **Never** 在共享工作树用 `git add .`、`git reset --hard`、`git clean` 隐藏他人修改，或把未核验的部署版本切到全量流量。

### Always do

1. **Always** 先写规则矩阵和验收路径，再实现最小纵切片；每个任务都有幂等键、积分值、失败态和证据。
2. **Always** 让服务端成为活动、积分、库存、订单和核销的唯一事实来源，所有变动写不可变流水并可重算。
3. **Always** 通过仓储接口隔离 CloudBase/本地实现；MVP 的单文档事务必须标注迁移边界，生产拆分独立集合。
4. **Always** 使用 CloudBase Storage `fileID` 和外部相册链接，接口按需刷新临时地址并提供图片失败占位/重试。
5. **Always** 在部署后验证目标提交、镜像/版本、`/health`、业务接口和 100% 流量，再清缓存做真机闭环。
6. **Always** 保留上一版可回滚版本，记录部署证据、数据迁移版本和运营操作；出现 404/旧内容先回滚或切流，不靠反复刷新掩盖。
7. **Always** 用最小权限子账号和环境变量管理云资源，导出 CRM 前明确字段、权限、用途和保留期限。
